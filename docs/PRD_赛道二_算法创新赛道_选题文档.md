## 1. 选题结论 + 淘汰逻辑

### 1.1 结论

**选赛题 2：AI+软件创新。**

选题理由一句话：赛道通知要求"深挖算法潜力、拓展算法应用边界，围绕'人工智能+'科技、产业、消费、民生、治理等重点领域，遴选一批优秀'人工智能+'新成果、新产品、新应用、新场景"--本项目交付的正是一个完整、可运行、可演示的 AI 软件产品：以 PP-YOLOE+-m 为引擎的农业病害智能检测软件系统（统一推理引擎 + CPU/GPU 双后端 + Gradio 6.24.0 Web 平台 + CLI 批量工具），且"AI+农业"直击通知点名的民生领域。

### 1.2 七个赛题逐一评估

| 赛题 | 匹配度 | 判定 | 核心理由 |
|---|---|---|---|
| 1. 算法模型创新 | ★★☆☆☆ | ❌ 排除 | 最终模型 PP-YOLOE+-m 为**官方结构零自定义模块**（CSPResNet + CustomCSPPAN + PPYOLOEHead 原样使用），增益来自数据修复与容量放大（`configs/ppyoloe_plus_crn_m_100e_agrivision.yml` 注释明确"不引入任何其他算法机制"）。多个自定义损失/辅助监督方向（CGPM、类加权 VFL、密度感知校准、CG-ACS）已实验并判定失败归档（`PROJECT_FINAL_STATUS.md` §2.2）。以"无新算法模块"的现状参加算法创新赛，等于拿最短板竞争。 |
| **2. AI+软件创新** | ★★★★★ | **✅ 选定** | 赛题考察 AI 软件产品的完整性与创新性。项目是已交付的软件实体：后端抽象引擎（`inference/detector.py`）、批量引擎（`inference/batch_infer.py`）、Web 平台（`web/app.py`）、CLI（`inference/infer.py`）、一键环境/训练/评估脚本（`scripts/`）、15 张演示案例（`web/demo_data/`）--软件工程完整度（失败隔离、单例加载、启动自检、多后端可插拔、真实 FPS 口径）即创新叙事主体。 |
| 3. AI+硬件创新 | ★☆☆☆☆ | ❌ 排除 | 需要硬件产品/嵌入式实体。项目无硬件（RK3588 仅软件侧预留接口，未转换未部署）；本地与团队均无硬件开发条件。 |
| 4. AI+场景创新 | ★★★☆☆ | ❌ 排除 | 赛题原文重点："结合**大模型、智能体**等前沿技术……探索人工智能+新应用、新服务、新业态、新模式，打造具有**颠覆性**、社会效益或商业潜力的场景化解决方案"。项目**没有**大模型/智能体/RAG 能力（事实库 §15 明确为无），短期内补齐需要从零引入全新技术栈，与"复用项目底座、不重复造轮子"原则冲突；且"颠覆性"定调下，以纯检测 Web 工具参赛竞争力不足。相比之下赛题 2 的评审重心（软件产品本身）与项目能力精确重合。 |
| 5. AI+学科交叉 | ★★☆☆☆ | ❌ 排除 | 需要"AI+非计算机学科"的实质性交叉融合与学科侧创新证据（如 AI+生物/医学的方法论贡献）。项目仅是 AI 应用于农业数据，未产出植保/农学侧的可验证新知识。 |
| 6. AI+创新创业 | ★★☆☆☆ | ❌ 排除 | 需要 BP、商业模式、市场验证、股权/财务规划等商业化包装与运营证据。项目无用户/收入/融资事实，材料只能靠设想填充，真实性风险高。 |
| 7. AI+OPC 创新创业 | ★★☆☆☆ | ❌ 排除 | 同上，且 OPC 方向有额外课程/孵化要求，超出团队现有投入范围。 |

**淘汰逻辑总结**：赛题 1 以"算法模块创新"为硬门槛，项目恰恰是零自定义模块（诚实工程路线）；赛题 3 需硬件、赛题 4 需大模型/智能体、赛题 5 需学科交叉实证、赛题 6/7 需商业验证--均为零积累方向。唯一既有实体又有差异化故事的，是赛题 2 的"AI 软件产品"叙事。

## 2. 项目名称 + 一句话简介

- **项目名称**：AgriVision · AI 农业病害智能检测软件平台（Agricultural Disease Intelligent Detection System）
- **一句话简介**：一款基于 PP-YOLOE+-m 的轻量级作物病害检测软件，内置统一多后端推理引擎（CPU/GPU 可插拔、边缘 NPU 预留）与浏览器即用的 Web 检测平台，让种植户与植保人员"传图即检、批量即报"，覆盖番茄/苹果/葡萄 13 类叶部病害。

## 3. 背景与痛点（引用赛道通知原文）

赛道通知总纲："聚焦算法应用创新，鼓励参赛选手深挖算法潜力、拓展算法应用边界，围绕'人工智能+'**科技、产业、消费、民生、治理**等重点领域，遴选一批优秀'人工智能+'新成果、**新产品、新应用、新场景**。"

落到本项目所切入的"AI+农业"民生场景，痛点具体为：

1. **识病门槛高**：作物病害识别长期依赖专家经验，基层种植者"看不准、问不到"，识别不及时导致防治窗口错过；
2. **AI 能力"看得见、用不上"**：学术界大量病害检测模型停留在离线评测脚本，缺少普通人可用的产品形态--这正是通知要求"新产品、新应用"所指向的缺口。本项目以**免安装的浏览器 Web 平台 + 一行命令的 CLI 批量工具**补上最后一公里；
3. **部署环境碎片化**：AI 软件常常绑定特定算力环境。本项目以统一后端抽象（CPU/GPU 自动切换 + RKNN 预留）保证同一套软件在笔记本 CPU 与服务器 GPU 上行为一致（已做逐位一致性验证）；
4. **工具可信度存疑**：AI 结果常被过度包装。本软件坚持真实口径展示（真实计时 FPS、置信度为模型原始输出、附"不等同于专业植保诊断"免责声明），以可信工程打动用户。

## 6. 技术方案

### 6.1 软件架构（分层解耦）

```
┌─ 交互层  Gradio 6.24.0 Web（web/app.py） / CLI（inference/infer.py）
├─ 服务层  单例管理 + 启动自检（web/backend.py）
├─ 引擎层  DetectorBackend 统一接口（inference/detector.py）
│           ├─ PaddleBackend（paddle_cpu / paddle_gpu，已实现）
│           └─ RKNNBackend（rknn_reserved，占位预留）
├─ 处理层  预处理（Resize/Normalize/Permute，与官方 reader 逐位一致）
│           后处理（Detection 结构 / 置信度过滤 / 批次统计，inference/postprocess.py）
│           批量引擎（失败隔离 / 产物落盘 / 真实 FPS，inference/batch_infer.py）
└─ 模型层  PP-YOLOE+-m（PaddleDetection v2.9.0 推理框架，不改源码）
```

关键设计：Web/后处理/可视化只依赖 `DetectorBackend` 接口与 `Detection` 数据结构，不依赖 Paddle 私有实现--新增任意后端只需实现同类接口并 `register_backend()` 注册，其余模块零改动（`inference/detector.py` 模块注释即此约定）。

### 6.2 Paddle 官方组件 + 论文映射

| 软件层组件 | 采用的官方实现 | 论文出处（arXiv） |
|---|---|---|
| AI 引擎（检测模型） | **PP-YOLOE+-m**：CSPResNet 骨干 + CustomCSPPAN 颈部 + PPYOLOEHead（PaddleDetection 官方结构，零自定义模块） | PP-YOLOE: An Evolved Version of YOLO - arXiv:2203.16250 |
| 推理框架 | PaddleDetection v2.9.0（源码零修改，路径经 `-o` 覆盖注入） | - |
| 深度学习框架 | PaddlePaddle 2.6.2（训练/评估，AutoDL RTX 4090）；本地 Windows Paddle 3.3.0 CPU 验证推理路径 | - |
| 分类损失 | Varifocal Loss（VFL） | arXiv:2008.13367 |
| 回归/质量损失 | Generalized Focal Loss | arXiv:2006.04388 |
| 标签分配 | Task Alignment Learning（TAL） | arXiv:2108.07755 |
| 预训练 | Objects365-m 官方预训练权重 | arXiv:1908.00723 |
| Web 展示 | Gradio 6.24.0（非 Streamlit） | - |
| 边缘扩展（规划） | Paddle2ONNX -> RKNN-Toolkit2（未实施，仅架构预留） | - |

### 6.3 质量保证手段（软件工程亮点）

- 双后端一致性回归：CPU 与 GPU 对同 8 张 VAL 图逐目标比对（目标数 11=11，最大置信度差 0.000175、最大 bbox 差 0.04 px），证明"换后端不换结果"（`GPU_BATCH_INFERENCE_REPORT.md` §七）；
- 启动自检四项（模型文件/配置文件/类别映射/后端可用性），失败即中文明确报错（`web/backend.py`）；
- 输入鲁棒性：损坏图片单张失败不终止批次，失败明细落盘；非 ASCII 路径安全读取（`inference/batch_infer.py` read_image 用 np.fromfile + imdecode）；
- 演示数据安全：Web 启动时校验演示案例 source_path 必须位于 images/val 下，禁用 TEST 图片（`web/app.py` `_load_demo_cases`）。

## 10. 可行性分析

### 10.1 项目就绪度

软件主体 100% 已交付：引擎（`inference/`）、平台（`web/`）、模型（best_model.pdparams）、数据、演示案例、指标报告全部就绪且有实测证据。校赛增量仅为**报名 + 材料制作（PPT/视频/说明书）**，无任何技术攻关项，是 7 个赛题中边际成本最低的选择。

### 10.2 团队能力匹配

- **算法功底（蓝桥杯国奖）**：支撑了本项目的消融实验体系--固定判据（VAL mAP 提升 ≥+0.005 且无强类回退）、单变量控制、失败方向果断止损归档（`PROJECT_FINAL_STATUS.md` §2.2），这套"严格受控实验"方法论本身就是软件质量叙事的一部分；
- **限时开发节奏感**：项目在数周内完成数据审计->消融矩阵->最终训练（2.5 h/100 epoch）->独立验证->双后端推理->Web 交付的完整软件闭环，证明团队具备校赛 6 周节奏下的交付能力；
- **答辩经验**：蓝桥杯国奖答辩经验直接复用于校赛评审与省赛路演；项目自带 15 张自动播放演示模式作为现场演示兜底；
- **技术栈零新增**：Python / PaddlePaddle / PaddleDetection v2.9.0 / Gradio 6.24.0 / OpenCV 均为项目日常栈；本 PRD 不引入任何团队未掌握的技术。

### 10.3 环境可行性

- 正式指标引用 AutoDL RTX 4090 + Paddle 2.6.2 实测报告（材料层面引用，无需重跑）；
- 本地 Windows（Paddle 3.3.0 CPU）承担演示视频录制：启动必须走 `web\run_web.bat`（内置 chcp 65001 + PYTHONUTF8=1，规避中文 Windows GBK 解码错误）；版本不匹配为已知事项，仅本地演示用，指标不引用本地数字；
- 双环境差异本身就是软件"跨环境一致性"的演示素材（CPU/GPU 结果逐位一致已验证）。
